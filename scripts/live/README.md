# Живой шаг 6 §5.3 — MCP-подпроцесс на пишущем сервере

Чем снимается шаг 6 acceptance-матрицы
(`docs/product/plans/2026-09-14-contained-profile-root-implementation.md` §5.3)
в части «MCP-подпроцесс», и почему прошлый заход этот шаг не снял.

## Почему понадобился отдельный сервер

В заходе RAF-158 шаг 6 прошёл на JSON-RPC echo-сервере и оказался пустым:
echo отвечает одинаково при любом `HOME` и ничего никуда не пишет, поэтому
«MCP подключён и отвечает» ничего про изоляцию не доказывает. Под зелёным
шагом лежал настоящий дефект — stdio MCP собирал окружение мимо контракта
изоляции (`d00574e69`): `HOME`, `TMPDIR` и `XDG_*` копировались из процесса
движка, чей дом в `contained` намеренно не переезжает под корень профиля
(§2.2 плана).

Отсюда два файла рядом:

| Файл | Что делает |
|---|---|
| `mcp_write_probe_server.py` | stdio MCP-сервер без зависимостей, который **пишет** в `$HOME`, `$TMPDIR` (через `tempfile`) и во все четыре `XDG_*`, и ведёт манифест созданного |
| `capture_mcp_subprocess_env.sh` | снимает `ps`, `/proc/<pid>/environ` подпроцесса, держит `inotifywait` по §5 и выносит вердикт |

## Порядок на стенде

Ветка `hermes/raf158-mcp-subprocess-containment` поверх кандидата
`019c9250b`, клиентский конфиг, `contained`.

```bash
# 1. Наблюдение — ДО подключения сервера, из второго SSH.
scripts/live/capture_mcp_subprocess_env.sh watch ~/raf162

# 2. Подключение пробы.
hermes mcp add write-probe --command python3 \
    --args "$PWD/scripts/live/mcp_write_probe_server.py"
hermes mcp list          # шаг 6: список непустой
hermes mcp test write-probe   # подключение + два инструмента

# 3. Из Telegram, от лица клиента: «покажи список MCP» и один вызов
#    write_probe_file — шаг 6 требует именно вызов инструмента.

# 4. Снятие и вердикт (сервер должен быть ЖИВ в момент capture).
scripts/live/capture_mcp_subprocess_env.sh capture ~/raf162
scripts/live/capture_mcp_subprocess_env.sh verify  ~/raf162
scripts/live/capture_mcp_subprocess_env.sh stop    ~/raf162
```

`verify` возвращает 0 только если сошлось всё: `HOME=<root>/home`,
`TMPDIR`/`TMP`/`TEMP` и все четыре `XDG_*` внутри корня, каждый созданный
сервером файл внутри корня, и в `outside.log` нет ни одной записи с меткой
`mcp-write-probe` при подтверждённом наблюдении.

В отчёт идут четыре файла из `~/raf162`: `environ.txt`, `ps.txt`,
`outside.log`, `inotify.err`.

## Грабли, на которые уже наступили

**`inotifywait` умирает на старте, а лог остаётся пустым.** Упирается в
`max_user_watches`, если `/tmp` забит. Пустой `outside.log` без строки
`Watches established.` в `inotify.err` — не улика; `watch` это проверяет и
падает вслух, а `verify` считает неподтверждённое наблюдение расхождением.
Сузить набор каталогов: `WATCH_DIRS="/home/user /tmp/interesting"`.

**Нельзя искать процесс простым `pgrep -f`.** Он матчит подстроку по всей
командной строке, и в кандидаты попадает оболочка, в чьём `-c` имя пробы
просто упомянуто (та же `hermes mcp add … --args …`). Снять `environ` с
такой оболочки — получить чужой `HOME=/home/<оператор>` и ложный отказ
шага. Скрипт требует совпадения с целым полем argv, отсеивает оболочки и
сам watchdog, а при нескольких живых кандидатах не выбирает молча, а
показывает их и просит `PROBE_PID=<pid>`.

**Настоящий сервер — внук движка, а не сын.** `tools/mcp_tool.py`
подменяет argv на `python -m tools.mcp_stdio_watchdog -- <команда>`, так
что цепочка в `ps.txt` — движок → watchdog → сервер. Окружение снимается с
последнего.

**`tempfile` молча уходит в `/tmp`, если `TMPDIR` не существует.** Это не
баг пробы, а ровно то поведение, которое будет у любого чужого сервера:
несозданный `<root>/tmp` выглядит как утечка и должен ею считаться.

## Репетиция вне стенда (что уже проверено)

Оба скрипта прогнаны локально на настоящем спавне через движок
(`tools.mcp_tool._connect_server` → watchdog → сервер), в двух режимах:

| Прогон | Дерево | Что показал `/proc/<pid>/environ` | Вердикт `verify` |
|---|---|---|---|
| на правке (`f5dba90d6`) | `hermes/raf158-mcp-subprocess-containment` | `HOME=<root>/home`, `TMPDIR`/`TMP`/`TEMP`=`<root>/tmp`, все `XDG_*` под `<root>/home`, `HERMES_REAL_HOME` наружу | 0 расхождений, `outside.log` пуст |
| без правки (`019c9250b`) | кандидат | `HOME` — дом движка, `TMPDIR=/tmp`, `XDG_CACHE_HOME` наружу, остальных `XDG_*` нет | 10 расхождений, 9 записей в `outside.log` |

То есть проба ловит тот самый дефект живьём, а не только в тесте.
Репетиция не заменяет стенд: там другой клиентский конфиг, другой путь
вызова (Telegram, а не прямой вызов сессии) и настоящий дом оператора.
